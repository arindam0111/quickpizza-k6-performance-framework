# Performance Result Comparison

## 1. Overview

The performance result comparison utility compares two analyzer summary files:

* **Baseline** - previously generated performance result
* **Current** - latest performance result

The utility identifies measurable changes and classifies them as:

* `IMPROVEMENT`
* `REGRESSION`
* `NO_CHANGE`
* `NOT_COMPARABLE`
* `NOT_AVAILABLE`

The comparison utility is implemented in:

```text
analyzer/compareReports.js
```

---

## 2. Prerequisite

Both input files must be analyzer summary JSON files generated by:

```text
analyzer/analyzeReport.js
```

Example:

```powershell
node analyzer/analyzeReport.js reports/load/load-result.json
```

This produces:

```text
reports/load/load-summary.json
```

---

## 3. Running the Comparison

Run:

```powershell
node analyzer/compareReports.js <baseline-summary> <current-summary>
```

Example:

```powershell
node analyzer/compareReports.js reports/load/baseline-summary.json reports/load/load-summary.json
```

The comparison report is written next to the current summary.

Example:

```text
reports/load/load-comparison.json
```

---

## 4. Comparison Requirements

The baseline and current summaries must:

1. Be valid JSON.
2. Contain the required summary sections.
3. Contain an execution scenario.
4. Use the same scenario.

Required sections:

```text
execution
reliability
performance
business
endpoints
```

### Scenario Validation

The comparison stops if the scenarios do not match.

For example:

```text
baseline = load_test
current  = smoke_test
```

This prevents an invalid comparison between different execution profiles.

---

## 5. Compared Metrics

### Performance

The following metrics are compared:

```text
performance.httpRequestDuration.avg
performance.httpRequestDuration.p95

performance.transactionTime.avg
performance.transactionTime.p95

performance.iterationDuration.avg
performance.iterationDuration.p95
```

For performance metrics, lower values are considered better for comparison classification.

---

### Reliability

The following metrics are compared:

```text
reliability.checks.rate
reliability.httpRequestFailed.rate
reliability.loginSuccessRate.rate
```

Comparison direction:

| Metric                   | Direction        |
| ------------------------ | ---------------- |
| checks rate              | Higher is better |
| http request failed rate | Lower is better  |
| login success rate       | Higher is better |

---

### Business Metrics

The following are included:

```text
business.successfulOrders
business.scenarioExecutions
```

These metrics are reported for informational purposes.

They are not classified as performance regressions or improvements.

---

### Endpoint Metrics

The following endpoint metrics are compared:

```text
register
login
create_order
get_order
list_orders
verify_order
delete_order
```

For each endpoint:

```text
avg
p95
```

are compared.

Endpoint response-time comparison uses the lower-is-better rule.

---

## 6. Comparison Tolerance

The default comparison tolerance is:

```text
5%
```

This value is defined in:

```javascript
const REGRESSION_TOLERANCE = 5;
```

Changes within ±5% are classified as:

```text
NO_CHANGE
```

---

## 7. Classification Rules

### Performance Metrics

For lower-is-better metrics:

```text
increase > 5%  → REGRESSION
decrease > 5%  → IMPROVEMENT
otherwise      → NO_CHANGE
```

Example:

```text
Baseline p95 = 379.02 ms
Current p95  = 450.00 ms
Change       = +18.73%
Result       = REGRESSION
```

---

### Higher-Is-Better Metrics

For reliability metrics such as checks rate and login success rate:

```text
increase > 5%  → IMPROVEMENT
decrease > 5%  → REGRESSION
otherwise      → NO_CHANGE
```

---

### HTTP Request Failure Rate

For `http_req_failed`, lower values are better.

```text
increase > 5%  → REGRESSION
decrease > 5%  → IMPROVEMENT
otherwise      → NO_CHANGE
```

A special rule applies when the baseline value is zero.

If:

```text
baseline = 0
current  > 0
```

the result is:

```text
REGRESSION
```

The percentage change is:

```text
null
```

because percentage change from zero cannot be calculated meaningfully.

---

## 8. Absolute and Percentage Change

Each comparable metric contains:

```json
{
  "baseline": 379.02,
  "current": 350,
  "absoluteChange": -29.02,
  "percentageChange": -7.66,
  "status": "IMPROVEMENT"
}
```

### Absolute Change

Represents the direct difference:

```text
current - baseline
```

### Percentage Change

Represents the relative change from the baseline.

Output values are rounded to two decimal places for readability.

The classification itself uses the underlying calculation precision.

---

## 9. Missing Metrics

Missing metrics are not treated as zero.

If a metric exists in the baseline but is unavailable in the current summary, the result is:

```text
NOT_AVAILABLE
```

Example:

```json
{
  "baseline": 4628,
  "current": null,
  "absoluteChange": null,
  "percentageChange": null,
  "status": "NOT_AVAILABLE"
}
```

This prevents missing test data from being incorrectly interpreted as a performance improvement.

---

## 10. Missing Endpoints

If an endpoint exists in only one of the two summaries, it is classified as:

```text
NOT_COMPARABLE
```

Example:

```json
{
  "baseline": 329.62,
  "current": null,
  "absoluteChange": null,
  "percentageChange": null,
  "status": "NOT_COMPARABLE"
}
```

The endpoint is not treated as a zero-duration request.

---

## 11. Regression Summary

The comparison report contains a regression summary.

Example:

```json
{
  "status": "REGRESSION_DETECTED",
  "regressionCount": 2,
  "improvementCount": 1,
  "noChangeCount": 20,
  "notComparableCount": 0
}
```

The overall comparison status is:

```text
REGRESSION_DETECTED
```

when one or more applicable metrics are classified as regressions.

Otherwise:

```text
NO_REGRESSION_DETECTED
```

---

## 12. Regression Details

Detected regressions are also collected in:

```text
regressions
```

Example:

```json
{
  "metric": "performance.httpRequestDuration.p95",
  "baseline": 379.02,
  "current": 450,
  "absoluteChange": 70.98,
  "percentageChange": 18.73,
  "status": "REGRESSION"
}
```

This provides a concise list of metrics requiring investigation.

---

## 13. Business and Execution Metrics

Business and execution metrics are included for context.

They are marked:

```text
INFORMATIONAL
```

They do not contribute to:

```text
regressionCount
improvementCount
noChangeCount
```

This prevents differences in execution volume from being interpreted as application performance regressions.

---

## 14. Thresholds vs Comparison

k6 thresholds and historical comparison answer different questions.

### k6 Thresholds

Thresholds determine whether the current run meets predefined performance expectations.

Example:

```text
http_req_duration p95 < 2000 ms
```

### Comparison

Comparison determines whether the current run changed relative to a baseline.

Example:

```text
Baseline p95 = 379.02 ms
Current p95  = 450.00 ms
Change       = +18.73%
Result       = REGRESSION
```

A run can therefore:

* pass all k6 thresholds, while still showing a regression compared with a previous run;
* fail a threshold, while showing an improvement compared with an even slower baseline.

These are separate evaluation mechanisms.

## 15. Example Workflow

A typical workflow is:

```text
Run k6 test
    ↓
Generate native JSON result
    ↓
Run analyzer
    ↓
Generate analyzer summary
    ↓
Compare current summary with baseline
    ↓
Review regression summary
    ↓
Investigate significant regressions
```

Example commands:

```powershell
k6 run --insecure-skip-tls-verify --out json=reports/load/load-result.json tests/quickPizzaE2E.js

node analyzer/analyzeReport.js reports/load/load-result.json

node analyzer/compareReports.js reports/load/baseline-summary.json reports/load/load-summary.json
```

## 16. V1 Scope

The comparison utility currently supports:

* baseline vs current comparison
* performance metrics
* reliability metrics
* endpoint response-time comparison
* absolute changes
* percentage changes
* 5% tolerance
* regression detection
* improvement detection
* no-change detection
* missing metric handling
* missing endpoint handling
* zero-baseline handling

* JSON comparison output

## 17. V1 Limitations

The current implementation does not provide:

* HTML reports
* charts
* Grafana dashboards
* historical result storage
* automatic baseline selection
* CI/CD integration
* statistical significance analysis
* capacity prediction
* trend forecasting
* automatic performance diagnosis
* endpoint-specific regression thresholds
* group-level regression comparison

These can be considered separately if required in the future.

## 18. Output Location

Comparison reports are generated beside the current summary.

Example:

```text
reports/
└── load/
    ├── load-summary.json
    └── load-comparison.json
```

Generated reports remain excluded from Git through the existing `.gitignore` configuration.

---

## 19. Interpretation Guidance

A comparison result should be treated as an investigation signal rather than an automatic explanation of root cause.

For example:

```text
REGRESSION
performance.httpRequestDuration.p95
+18.73%
```

indicates that the measured p95 increased beyond the configured tolerance.

Possible causes require further investigation, such as:

* application changes
* database behavior
* test-data differences
* environment conditions
* infrastructure changes
* network conditions
* workload differences

The comparison utility identifies the measurable change; it does not determine the root cause.

---

## 20. Summary

The comparison utility provides a lightweight V1 mechanism for detecting meaningful performance changes between two k6 analyzer summaries.

Its primary purpose is to make performance regression analysis repeatable and machine-readable without introducing a larger reporting or dashboarding system.
