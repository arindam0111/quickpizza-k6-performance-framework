# Performance Report Analysis

## Purpose

This document defines the standard approach for analyzing performance-test
results generated by the QuickPizza k6 performance-testing framework.

The objective is to provide a consistent structure for reviewing:

* Test execution
* Reliability
* Response time
* Endpoint performance
* Business metrics
* Performance thresholds

This document defines the analysis model. It does not currently implement
automated report generation or HTML reporting.

---

# 1. Execution Summary

The execution summary provides basic information about the performance-test run.

| Metric        | Description                      |
| ------------- | -------------------------------- |
| Scenario      | Configured k6 execution scenario |
| Start Time    | Test execution start timestamp   |
| End Time      | Test execution end timestamp     |
| Duration      | Total test execution duration    |
| VUs           | Virtual-user information         |
| Iterations    | Number of completed iterations   |
| HTTP Requests | Total HTTP requests generated    |

Current supported execution modes:

* `smoke_test`
* `load_test`
* `negative_test`

The positive performance test supports `smoke_test` and `load_test` through
`TEST_SCENARIO`.

The negative API test is executed independently through:

```text
tests/negative/ratingNegativeTest.js
```

---

# 2. Reliability Summary

The reliability section determines whether the application behaved correctly
during the test.

## Checks

The k6 `checks` metric validates:

* HTTP response status
* Response content
* Authentication
* Business workflow behavior
* Data integrity

Configured threshold:

```text
checks: rate > 0.95
```

## HTTP Request Failures

The `http_req_failed` metric identifies failed HTTP requests.

Configured threshold for the positive performance test:

```text
http_req_failed: rate < 0.05
```

Expected HTTP errors in the negative test are evaluated separately through
explicit response-status checks.

## Login Success Rate

The custom `login_success_rate` metric measures authentication success.

Configured threshold:

```text
login_success_rate: rate > 0.98
```

---

# 3. Performance Summary

The performance section focuses on response time and transaction behavior.

## HTTP Request Duration

The standard k6 metric `http_req_duration` is used to evaluate API response
time.

Primary threshold:

```text
p(95) < 2000 ms
```

Endpoint-specific thresholds are also configured.

## Transaction Time

The custom `transaction_time` metric measures the duration of the complete
business workflow.

Configured threshold:

```text
p(95) < 25000 ms
```

## Iteration Duration

The k6 `iteration_duration` metric measures the total duration of a k6
iteration.

Configured threshold:

```text
p(95) < 30000 ms
```

---

# 4. Endpoint Performance

Endpoint performance is analyzed using the endpoint-specific `name` tags
generated by the framework.

| Transaction    | API Operation       |
| -------------- | ------------------- |
| `register`     | User registration   |
| `login`        | User authentication |
| `create_order` | Rating creation     |
| `get_order`    | Rating retrieval    |
| `list_orders`  | Rating listing      |
| `verify_order` | Rating verification |
| `delete_order` | Rating deletion     |

The historical `order` terminology is intentionally retained in the current
framework transaction names.

For each endpoint, future analysis may consider:

* Average response time
* p95 response time
* Maximum response time
* Request count
* HTTP status
* Failure rate
* Threshold status

---

# 5. Business Metrics

The framework includes custom metrics to measure business-level behavior.

## Successful Orders

The `successful_orders` counter tracks successfully completed business
transactions.

The metric name is retained for framework consistency with earlier project
terminology.

Configured threshold:

```text
count > 20
```

This threshold is primarily relevant to load-test execution.

A single smoke iteration is expected to produce fewer than 20 successful
transactions, so this threshold may be breached during a smoke test by design.

## Scenario Executions

The `scenario_executions` counter tracks completed framework executions and
includes the scenario tag.

Examples:

```text
scenario=smoke_test
```

```text
scenario=load_test
```

---

# 6. Threshold Summary

Thresholds provide the primary automated performance-validation criteria.

The analysis should identify:

* Passed thresholds
* Failed thresholds
* Expected threshold breaches
* Thresholds relevant to the selected execution mode

Important thresholds include:

| Metric               | Threshold      |
| -------------------- | -------------- |
| `http_req_duration`  | p95 < 2000 ms  |
| `http_req_failed`    | rate < 0.05    |
| `checks`             | rate > 0.95    |
| `iteration_duration` | p95 < 30000 ms |
| `transaction_time`   | p95 < 25000 ms |
| `login_success_rate` | rate > 0.98    |
| `successful_orders`  | count > 20     |

Endpoint and group-level thresholds are defined in:

```text
config/thresholds.js
```

Negative-test thresholds are maintained separately in:

```text
config/negativeThresholds.js
```

---

# 7. Load Behavior Analysis

For the configured load scenario, performance results should be reviewed
against the configured load profile.

Current profile:

```text
30s  ->  5 VUs
1m   -> 10 VUs
2m   -> 15 VUs
1m   -> 10 VUs
30s  ->  0 VUs
```

The analysis should consider:

* Virtual-user progression
* Request volume
* Response-time behavior
* Error rate
* Check rate
* Transaction performance
* Threshold compliance

The purpose is to understand behavior under the configured load, not to
establish production capacity for the public QuickPizza service.

---

# 8. Smoke vs Load Analysis

Smoke and load executions serve different purposes.

## Smoke Test

The smoke scenario verifies:

* Framework execution
* API connectivity
* Authentication
* End-to-end workflow
* Basic response validation
* Threshold configuration

The smoke test is not intended to demonstrate sustained load behavior.

The smoke test uses:

```text
1 VU
1 iteration
maxDuration: 1m
```

## Load Test

The load scenario evaluates:

* API response behavior under increasing VUs
* Request volume
* Transaction performance
* Error behavior
* Threshold compliance
* Business transaction throughput

The configured load profile reaches:

```text
15 VUs
```

Results from smoke and load executions should therefore be interpreted
according to their different execution models.

---

# 9. Negative-Test Analysis

Negative API testing is analyzed separately from positive performance testing.

Current scenarios include:

```text
Invalid Rating ID
        |
        v
       404

Invalid Authentication
        |
        v
       401

Invalid Rating Data
        |
        v
       400
```

The primary validation criteria are the expected HTTP status codes and k6
checks.

The `http_req_failed` metric should not be interpreted in isolation for the
negative test because expected HTTP error responses can contribute to the
metric.

The negative test uses its own k6 scenario:

```text
negative_test
```

and is executed directly through:

```text
tests/negative/ratingNegativeTest.js
```

# 10. Current Analysis Workflow

The current result-analysis workflow is:

```text
Execute k6 Test
      |
      v
Generate JSON Result
      |
      v
Inspect Execution Metadata
      |
      v
Review Reliability Metrics
      |
      v
Review Response-Time Metrics
      |
      v
Review Business Metrics
      |
      v
Review Endpoint Performance
      |
      v
Review Thresholds
      |
      v
Analyze Load Behavior
```

The native k6 JSON result is stored as line-delimited JSON (JSONL).

Each line represents a k6 result object such as:

* Metric definitions
* Metric points
* Tags
* Threshold information
* Execution data

The current framework does not yet calculate a custom summary from these raw
JSON points.

## 10.1 Iteration 22 Result Analysis

Iteration 22 validated the result-analysis workflow using controlled smoke and
configured load-test executions.

### Smoke Test Result

The controlled smoke execution used:

- Scenario: `smoke_test`
- Virtual Users: 1
- Iterations: 1
- HTTP Requests: 7
- Checks: 100%
- HTTP Request Failures: 0%
- Login Success Rate: 100%
- Transaction Time: 5.837 seconds
- HTTP Request Duration p95: 428 ms
- Iteration Duration p95: 5.3 seconds
- Successful Orders: 1

The `successful_orders` threshold was breached because the configured
threshold is `count > 20` and the smoke execution intentionally performs only
one business transaction. This is an expected smoke-test threshold breach.

### Load Test Result

The configured load execution used the complete five-stage load profile and
reached 15 VUs.

Results:

- Scenario: `load_test`
- Maximum VUs: 15
- Duration: 5 minutes
- Iterations: 685
- HTTP Requests: 4,795
- Checks: 100%
- HTTP Request Failures: 0%
- Login Success Rate: 100%
- Successful Orders: 685
- Transaction Time p95: 4.628 seconds
- HTTP Request Duration p95: 379 ms
- Iteration Duration p95: 4.62 seconds
- Interrupted Iterations: 0

All configured load-test thresholds passed during this execution.

### Smoke vs Load Observation

The smoke and load executions are interpreted according to their different
purposes.

The smoke execution validated framework connectivity, authentication, API
workflow behavior, and basic threshold configuration.

The load execution exercised the configured ramping-VU profile and produced
685 completed business transactions without HTTP request failures or failed
checks.

Across these two controlled executions, the primary reliability metrics
remained at 100%, while the observed HTTP request p95 remained below the
configured 2-second threshold.

The transaction-time p95 was 5.837 seconds during smoke execution and
4.628 seconds during the load execution. These values should not be treated
as a direct capacity comparison because the executions used substantially
different workloads and sample sizes.

### JSON Report Validation

The generated native k6 JSON reports were inspected to confirm that the
console results are supported by raw report data.

The load-test report contained 61,592 JSONL records.

The report included raw points for:

- `checks`
- `http_req_failed`
- `login_success_rate`
- `transaction_time`
- `successful_orders`
- `scenario_executions`
- Endpoint-specific `http_req_duration` data

Endpoint points included tags such as:

- `scenario`
- `name`
- `method`
- `status`
- `group`
- `url`

The native JSON report stores raw metric points and metadata rather than the
final aggregate statistics displayed by the k6 console.

Therefore, the current framework uses the k6 console output for aggregate
statistics such as average, p90, p95, and maximum values while retaining the
native JSON report as the raw execution record.

No custom statistics engine is implemented at this stage.

# 11. Future Automation

The current framework stores native k6 JSON results for analysis.

Future iterations may introduce:

* Automated JSON parsing
* Summary report generation
* HTML reporting
* Historical result comparison
* Performance trend analysis
* Charts and visualization
* CI/CD report publishing
* Automated threshold-result summaries

These capabilities will be introduced incrementally.

---

# 12. Scope

This document defines the analysis structure for the QuickPizza k6
performance-testing framework.

It does not currently:

* Modify k6 execution behavior
* Modify performance thresholds
* Generate HTML reports
* Calculate production capacity
* Establish production SLAs
* Automatically compare historical runs
* Automatically generate performance dashboards

The framework continues to use the public QuickPizza demo environment for
controlled performance-testing practice.
